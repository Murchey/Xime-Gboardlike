## 问题

用户反馈：双拼方案（紫光/搜狗/微软）下滑动输入准确性不高。

## 根源分析

### 1. 音节树只认全拼（核心问题）

`GlideSyllableTrie` 的 421 个音节是**全拼**音节表。解码器用它约束字母串的合法性：
只有能切成完整全拼音节的串才产出。

但双拼的编码结构不同：
- 全拼 `nihao` = n-i-h-a-o（5 字母，切成 ni|hao 或 ni|h|ao ...）
- 微软双拼 `nihk` = ni + hk（4 字母，切成 ni|hk）

`nihk` 不在全拼音节表里，解码器直接拒绝。所以双拼下滑动产出的键序列
被音节树过滤掉，只剩少量误打误撞的全拼串（如 `ni`），候选自然不准。

实测证据：双拼下滑动产出 `[ahu, agu, ashu, ai, su]`（全是全拼串），
而不是用户意图的双拼编码。

### 2. 双拼编码短，几何歧义大

双拼每音节 2 键，滑动轨迹短，几何上难以区分相近键。这是次要因素。

### 3. 语言模型未参与重排

当前候选排序只用几何代价 + Rime 候选位次。缺少整句级语言模型。

## 修复方案

### 方案 A：解码器支持双拼音节表（推荐）

按当前 schema 选择音节表：
- 全拼：现有 421 音节表
- 微软/搜狗/紫光双拼：各自的双拼音节表（声母键 + 韵母键的合法组合）

双拼音节表构造：以微软双拼为例，韵母键表（`a`=a, `b`=ou, `c`=iao, ..., `;`=ing）
与声母键组合，生成合法的双拼编码。

优点：解码器保持音节约束（几何 + 语言双重约束），准确率高。
缺点：每套双拼方案需要一份音节表（4 套），维护成本高。

### 方案 B：双拼下宽松解码（快速缓解）

双拼模式下解码器跳过音节树约束，产出几何最优的键序列，
交给 Rime 解码（Rime 的双拼 schema 天然做音节切分）。

优点：改动小，立即生效。
缺点：失去音节约束，候选数量增加，需要 Rime 侧更强的筛选。

### 方案 C：双拼键序列 → 全拼转换

滑动产出双拼键序列（`nihk`），按当前方案的韵母映射转全拼（`nihao`），
送全拼 schema 查 Rime。

优点：复用全拼的 Rime 词库与语言模型。
缺点：需要完整的双拼→全拼映射表（每方案一套），且与当前 schema 不一致时转换复杂。

## 推荐路径

**阶段 1（快速）**：方案 B —— 双拼下宽松解码，验证候选是否改善。
**阶段 2（完整）**：方案 A —— 为微软双拼先建音节表，验证后扩展到搜狗/紫光。

## 关于 gram 模型绑定

用户提出"强行绑定内置 gram 模型启用时才允许滑动输入"。

gram 模型是语言模型（N-gram），用于候选重排。它可以：
- 区分 `zhong`/`zong` 这类共线键（当前靠 Rime 词频）
- 提供整句级连贯性（当前缺）

绑定建议：
- **不建议**"禁用滑动"——那会损失功能
- **建议**"gram 模型启用时增强重排"——有 gram 时用它重排候选，无 gram 时退化为当前逻辑
- gram 模型体积小（N-gram 表），可常驻

## 验收标准

1. 微软双拼下滑 `n-i-h-k`，首选含「你好」
2. 搜狗/紫光双拼同理（各自的 nihao 编码）
3. 全拼回归不劣化（现有 73 项 glide 测试保持全绿）
4. 候选延迟 P95 < 250ms（8-20 字）

## gram 模型现状（已确认）

项目已有 N-gram 基础设施：
- `association/NgramFusionEngine.kt` — 融合引擎
- `association/NgramTrie.kt` — N-gram 前缀树
- `association/UserNgramCache.kt` — 用户 N-gram 缓存
- `settings/GrammarProfile.kt` — 语法配置
- `ui/settings/GrammarModelScreen.kt` / `GrammarParamsScreen.kt` — 设置界面

滑动候选重排可直接调用 `NgramFusionEngine`，无需新建模型。
