# 滑动准确性改进计划（基于 20 条真实小鹤双拼轨迹）

数据来源：`tmpImg/xime_glide_20261111_112000.jsonl`（2026-11-11 11:20 导出）
评测脚本：`node tools/glide-eval.mjs <jsonl>`（本文所有数字都由它算出，可复跑）

## 一、基线（16 条可用 + 4 条放弃）

| 指标 | 数值 |
|---|---|
| top-1 完全正确 | 4/16 (25%) |
| top-5 命中 | 5/16 (31%) |
| 编辑距离 ≤1 | 7/16 (44%) |
| **几何候选里含正解** | **5/16 (31%)** ← 解码器天花板 |

关键判断：**top-1(25%) 与几何可达(31%) 几乎持平**，说明瓶颈在几何解码，
不在后面的候选重排。此时去调 `RANK_PENALTY_WEIGHT` / `PHRASE_COHERENCE_BONUS`
不可能有大收益——先把几何候选里"根本没有正解"这件事解决。

## 二、错误分型（17 替换 / 10 多键 / 4 缺键）

- 替换 17 次，其中 **9 次是相邻键**（d=1）：这是空间模型可修的
- **多键 10 次 + 缺键 4 次 = 14 次是"键数不对"**，比替换还多
- 解码结果含连续重复字母 9/16，折叠后 7 条距离下降

## 三、按性价比排序的改进项

### P0：重采样饱和（8/20 撞上 MAX_SAMPLES=128）

`SAMPLE_STEP=0.25` 键，但长轨迹弧长可达 80 键 → 需要 320 个采样点，被截到 128。
实际步长退化为 0.63 键（g111046-20），采样点比手指实际停靠的键还稀。

数据证据：
- 饱和组 8 条，平均编辑距离 **2.63**
- 未饱和组 8 条，平均编辑距离 **1.25**

改法：`MAX_SAMPLES` 提到 256（或按弧长自适应），并保证"每个经过的键至少一个采样点"
（已有 `resampleByKeyRun` 可复用）。

### P1：同键连续（REPEAT_COST=0.8 太便宜）

现状：`REPEAT_COST=0.8` 只比普通字母贵 0.8，导致手指在键内稍微一停就被解成两个同键。

数据证据：9/16 出现连续重复字母，其中**音节内的重复全是错的**，
而期望里合法的重复（6/16 条含有）都跨音节边界。

**不能简单折叠重复**（会误伤 6 条合法的）。
**也不能用绝对下标的奇偶**——只要中间多/少一个键，后面角色整体错位（已用数据证实 5 条长度不等）。

正确改法：在 beam 里把"当前在音节的第几键"作为状态推进（schema 音节树本来就有），
"同键重复"只在**跨音节边界**时给低代价，在同一音节内给高代价。

### P2：多键/缺键（10/4，是最大的一类）

典型：`jtqullkuii` → 期望 `jtqulkui`（多了 ll 和 i）、`veixdsuruufa` → 期望 `veuihxdsuurufa`（少了两个键）。
说明"对齐哪些键"这件事本身不稳，而不是选错了键。

与 P0 高度相关：采样点不够时，两个相邻的对齐点之间跨了多个键，就会漏键或多键。
先做 P0，再看这一类还剩多少。

### P3：相邻键替换（9 次）

`t->g`、`m->n`、`l->k`、`e->r`、`i->u` 这类。这是 `ALIGN_SCALE=0.3` 与高斯热区的标定问题，
放在 P0/P1 之后再动，否则会被采样问题淹没。

### P4：候选不足 16 条

实测候选数只有 6~8 条（请求 16）。beam 在 `TOKENS_PER_SAMPLE=6` / `BEAM=10` 处收得太紧，
长句时正确编码根本没进候选集。这是"几何可达性只有 31%"的直接原因之一。

## 四、执行顺序与验收

1. **先做 P0 + P4**（纯参数/上限，不改算法结构）→ 重跑评测，看"几何候选含正解"从 31% 升到多少
2. **再做 P1**（同键重复按音节边界判定）→ 看多键数下降
3. **然后 P2**（对齐稳定性）
4. **最后 P3**（空间模型标定）
5. 全部定点后再考虑跨假设 gram / 重排序器

验收口径建议改成（原 README 里"追平全拼"不现实）：
- 几何候选含正解 ≥ 60%
- top-5 命中 ≥ 50%
- 编辑距离 ≤1 ≥ 70%

## 五、数据采集本身的改进

- 4 条标"无效内容"的样本，轨迹点数 320/时长 1140ms，远低于有效样本（1137 点 / 4344ms），
  其中 2 条只有 6~8 个点、89~103ms —— 是误触不是有效滑动。建议采集时过滤掉 <15 点或 <150ms 的轨迹。
- 需要补的样本类型：短音节（2~4 键）、含分号 ing、共线键（zh/z+s 这类）、跨行弧线。
- 当前 20 条全部是长句（10~18 键），短输入几乎没有覆盖。

## 六、第一轮改造实测（2026-11-11）

建了两台可复跑的"秤"，先量再改：

- `GlideIdealTraceTest`：把期望编码渲染成**精确经过键中心并停留**的合成轨迹，喂真实解码器。
  用来区分"搜索结构缺陷"和"真实轨迹噪声"。
- `GlideTraceReplayTest`：把真实 jsonl 原样回放给真实解码器（样本放
  `app/src/test/resources/glide/samples.jsonl`，已 gitignore）。

### 基线

| 指标 | 值 |
|---|---|
| 理想轨迹 top-1 | 3/5 |
| 理想轨迹命中 | 4/5 |
| 真实轨迹 top-1 | 3/16 |
| 真实轨迹几何可达 | 4/16 |

### 被数据否掉的三个猜想

1. **提高 MAX_SAMPLES（128→320）** —— top-1 反而 3→2。采样变密后按点累加的代价
   （停留罚分、连线偏差）同步放大，beam 更分散。**已回退。**
2. **放宽 beam（TOKENS 6→12、BEAM 10→20）** —— 指标完全不动。
3. **扫描 ALIGN_SCALE / LINE_SCALE / BACKTRACK_COST** —— 只有 LINE_SCALE 0.25→0.5
   把真实 top-1 抬到 4/16，其余均无变化；几何可达率始终被钉在 4~5/16。

结论：参数不是主要矛盾，**对齐搜索本身**才是（P2 的优先级由此升到最高）。

### 已落地的改动（唯一有正向收益的）

`SKIPPED_DWELL_COST` 4.0 → 1.0。

根因：一次停留要么被读成"对齐到该键"（代价 LETTER_COST=0.8），要么被读成
"跳过停留"（代价 4.0），要么被读成"同键按两次"（0.8+REPEAT_COST=0.8=1.6）。
4.0 让"跳过"成为最差选项，而 1.6 又比"正确对齐"贵，于是理想轨迹也被解成
`vhgr → vhggrr`、`jqxlui → jqxkluii` 这类多键串。

降到 1.0 后：

| 指标 | 改前 | 改后 |
|---|---|---|
| 理想轨迹 top-1 | 3/5 | **4/5** |
| 理想轨迹命中 | 4/5 | 4/5 |
| 真实轨迹 top-1 | 3/16 | 3/16 |
| 真实轨迹几何可达 | 4/16 | **5/16** |

注意：真实 top-1 没变——说明"几何能解出"和"最终排第一"是两件事，
后者要靠候选重排（P4 之后才该做）。

### 下一步（P2：对齐搜索）

理想轨迹仍有 1/5 解不出（`yipwwogu → ypwogu`，丢了中间的 p）。
这是"两个相邻对齐点之间跨了多个键"的典型表现，需要：
- 在 beam 状态里记录"已消费到第几个采样点"，对"跨度过大"的转移加惩罚；
- 或改成 DP（对每个采样点 × 每个音节状态做最优转移）而不是现在的逐字母扩展。


## 七、第二轮实测（2026-11-11，P2 探索）

### 先修正了"衡器"

上一轮的评测台用"声母 × 韵母"笛卡尔积造编码表（606 条），会生成 `yp`、`yie`
这类**不存在的音节**，解码器可以钻这个空子。已改为从 `GlideSyllableTrie` 的
421 个真实音节投影（407~414 条），与线上 `RimeEngine.getGlideSpellings` 同口径。

修正后基线变为：

| 指标 | 旧（假表） | 新（真实表） |
|---|---|---|
| 真实 top-1 | 3/16 | **4/16** |
| 真实几何可达 | 4/16 | **5/16** |
| 理想轨迹 top-1 | 4/5 | 4/5 |

### 关键诊断：11/16 是"根本不可达"

新增诊断输出把这 16 条拆成两类：

```
可达但非 top-1 = 1   （重排可救）
根本不可达     = 11  （必须改搜索）
```

**这推翻了"重排是下一步"的判断**：即使把重排做到完美，也最多 5/16。
瓶颈 100% 在解码搜索。

### 已验证：不是合法性约束挡的

16 条正解**全部**能按"两键一音节"切开（407 条真实编码表），一条都不例外。
所以不是音节表不够宽，是 beam 没走到那里。

### 被否掉的改动

1. **跨度惩罚（SPAN_COST）**：给"相邻对齐点跨多个采样点"加代价。
   0.02/0.1/0.3 完全无变化，0.6/1.0 开始伤真实 top-1。**已回退。**
2. **候选数 16→32→64**：可达 5→6→6，top-1 不动，边际归零。**已回退到 16。**
3. **SKIPPED_DWELL_COST 再扫描**：0.5 同 1.0；2.0 让理想 top-1 退回 3/5。
   确认 1.0 是最优点。**保持。**

### 为什么 `yipwwogu` 解不出（代表性案例）

理想轨迹里 `yipwwogu` → `yipowogu`（w 被 o 替代）。
查几何：p 键中心 (1026,83)、o 键中心 (918,83)、w 键中心 (162,83) 在**同一条水平线上**，
p→w 的连线**正好穿过 o 键中心**。所以 `yipowogu` 在几何上是完全合理的读法。

这不是缺陷，是双拼"跳 8 个键"本身不现实——我的合成轨迹造了一个不合手的场景。
**判定：这条不该作为改进目标**，理想台的目标应该是"每步移动 ≤2 键"的合理轨迹。

### 下一轮方向（改搜索结构，不是调参）

真正的结构问题：当前是"逐字母扩展 + 每个采样点剪枝到 TOKENS_PER_SAMPLE"，
每层剪枝只看该点上的绝对代价，**丢掉了"部分路径的整体最优"**。
长句（16~18 键）时路径要跨 200+ 采样点，中间任何一层剪错就永久丢失。

建议改成**保留每层全局 best-K 路径**（而不是每点 best-K），或者
对采样点做 DP：
- 状态 =（已对齐字母数, 当前音节树状态, 当前采样点）
- 转移 = 对齐下一字母到 j+Δ，Δ 由键距约束
- 这样"某点上的次优路径"只要整体仍可能最优就不会被剪掉。

预期：可达率从 5/16 提到 ≥10/16。


## 八、第三轮：结构改造尝试（2026-11-11）

本轮目标是「改搜索结构」，不再是调参。**结论：四种结构改法都没能提升可达率。**

### 先排除了三个可疑点（都是「不是它」）

| 假设 | 验证方法 | 结论 |
|---|---|---|
| 抬手位置不在末键附近，假设无法收尾 | 16 条里 13 条末点就在期望末键附近 | 不成立 |
| reach[] 预过滤把字母挡掉 | 16 条正解的每个字母都有可用采样点 | 不成立 |
| 正解无法单调对齐（顺序不可行） | 贪心检查 16/16 全部可单调对齐 | 不成立 |

### 四种结构改法，全部无效

1. **按字母数分层剪枝**（同一采样点上不同字母数不互相挤占名额）
   → 指标完全不变（top-1 4/16、可达 5/16）。
   保留该改动（修结构隐患），但**不带来准确率提升**，已在注释中如实标注。
2. **收尾容差**（允许末字母不精确落在最后一个采样点）
   → 可达不变，top-1 从 4 掉到 **1**。已回退。
3. **放宽 TOKENS_PER_SAMPLE 6→32→40**
   → 完全不变。说明瓶颈不在「每个点留几条」。
4. **放宽 BEAM 10→25→50**
   → 完全不变。说明剪枝裕度也没卡住正解。

（把两者同时放到 40/60 仍只有 5/16；再放大到 500/100000 直接 OOM，
说明状态空间会指数爆炸，不能靠「不剪枝」暴力解决。）

### 一个重要的定量发现

用解码器的代价公式离线重算「正解」与「解码输出」的总代价，9 条可计算样本里
**6 条正解代价更低**，但解码器给出的却是更贵的答案。

**这意味着搜索确实没找到最优解，是实现缺陷而非模型不足。**
但上面四种改法都没修好它 —— 说明缺陷在更底层的举证/记账方式，
下一轮应该直接逐样例跟踪一条失败样本的完整 beam 演化，而不是继续猜。

### 也验证了 line 项不可动

lines[from][to] 这条连线/回溯代价项，去掉或权重减半都会让指标**归零**
（top-1 0/16、可达 0~2/16）。它是结构性的，不能简化。

## 九、第四轮：逐层 beam dump 定位（2026-11-11）

放弃「猜改法」，改为给解码器加 debugSink，把一条失败样本（g111046-12，
期望 jtqulkui，实际 jtqullui）的逐层 beam 内容全部打印出来。

### 三个确定的结论

1. **正解确实存在于搜索空间**：把 TOKENS_PER_SAMPLE 临时调到 50 后，
   dump 显示 jtqulkui 在 L8 精确命中，代价 8.88（当层最低之一）。
2. **但默认参数下它进不了最终候选**：limit=200 时位次 = -1（根本不出现）。
   这个矛盾说明 finals 的收集/截断还有一处状态管理问题。
3. **即使出现，它也不是最优**：首位 jtqullui 代价 8.21，正解代价 9.77。

### 关键定性：这个样本本身是真歧义，不是 bug

查轨迹在 l 键附近的实际采样：x 从 919 一路到 999，y 停在 259 附近约 1.5 秒，
然后折返回 k 键（864,249）停住。也就是说手指实实在在在 l 上待过并回来了。

- 意图 jtqulkui 需要读成：经过 l 不停、在 k 停下
- 解码给出 jtqullui：把 l 读成一次按键（折返=重复）

两者在几何上都成立。这不是解码器该修的 bug，而是双拼编码密度高导致的固有歧义，
需要靠语言模型（哪个词更常见）而不是几何来消解——正好回到 doc 开头 P4 之后
「跨假设 gram」的结论。

### 本轮试过并回退的

| 改动 | 结果 |
|---|---|
| prune 按字母数分层（BEAM 用组内 floor） | 指标不变，保留（修结构隐患） |
| finals 不再截断到 limit | top-1 4→2、可达 5→2，**已回退** |
| 收尾改用 minByOrNull 取代 lastOrNull | top-1 4→2，**已回退**（原语义是对的） |
| TOKENS_PER_SAMPLE 6→50 | 正解进入候选但指标不变、耗时增加，**已回退** |

### 产出

- 新增 GlideAmbiguousRepeatTest：把「这个样本是歧义而非丢失」固化下来，
  防止以后误判为搜索缺陷而做无用的结构改造。
- 移除 debugSink 钩子（生产代码不留调试路径）。

### 修正上一轮的判断

上一轮写「9 条可比样本里 6 条正解代价更低，确认是搜索实现缺陷」。
这个结论下得太早：那 6 条的代价是用简化脚本估的（漏了 lines 的回溯项与
dwell 项），逐层 dump 显示真实代价顺序未必如此。至少 g111046-12 这一条，
正解代价确实更高。需要逐条 dump 才能确认那 6 条里有多少属于同类歧义。

## 十、对「瓶颈是缺可比较语言模型分数」一文的核对（2026-11-11）

### 二、被我们的实测否掉的（文中列为改进项）

1. **「用双拼奇偶约束补回剪枝」（文中第 3 条）**
   已验证不可行：只要编码中间多/少一个键，后面所有位置的角色（声母位/韵母位）
   就整体错位。16 条真实样本里有 5 条长度不等，绝对下标奇偶完全失效。
   而且解码器已经用 schema 音节树在维护这个状态，不需要再加。

2. **「先改打分、后建 benchmark」的隐含顺序**
   文中把 benchmark 列为 (a)、打分改动列为第 2 节，暗示可以先改。
   实测：连续四轮结构改造（MAX_SAMPLES、beam 宽度、跨度惩罚、剪枝分层）
   **全部零收益或有负收益**，因为没有 benchmark 时根本分不清改对了没有。
   正确顺序是：**先建 benchmark（已完成）→ 再改打分**。

### 五、本轮的实际进展（第五轮）

在 11 条不可达样本里定位到一个**真 bug**（不是歧义）：

样本 g111046-12，期望 `jue qu ling shi`(jtqulkui)，解码成 `jue qu liang shi`(jtqullui)。
查轨迹：手指从 k 快速滑到 l（每步 1~4ms，**无任何停留**）再折回 k，
并在 k 上真正停住（距键心 4px，停留 142ms）。
所以正确解读是「经过 l、停在 k」，解码器却把 l 读成了两次按键。
根因：`GlideRepeatGesture` 给出折返线索后，旧代码**无条件**减 2.4 分，
不看折返区间里有没有停留证据。

改法：`Repeat` 增加 `hasDwell` 字段，只有折返区间内存在停留样本时才给折扣，
否则按 `REPEAT_NO_DWELL_PENALTY` 轻微惩罚。

实测（16 条真实样本）：

| 指标 | 改前 | 改后 |
|---|---|---|
| top-1 | 4/16 | **5/16** |
| 几何可达 | 5/16 | **8/16** |
| 根本不可达 | 11 | **8** |
| 理想轨迹 top-1 | 4/5 | 4/5 |

逐条看：5 条变好（含 g111046-12 直接成为首选）、2 条变差（距离各 +1/+2）。
罚分取值在 0.05~4.0 之间结果一致，说明起作用的是「取消无条件折扣」这个二元改动。

### 六、对文中「天花板」一节的回应

同意「双拼纠错冗余天生更少」这个判断，且有数据支撑：
16 条样本里 11 条键数完全正确（只错在某个键读成邻键），
而「邻键替换」只占全部编辑操作的 35%，其余 65% 是多键/缺键/远距替换。
这说明瓶颈确实不在空间模型精度，而在「哪些键算被按了」的对齐层。

但**不完全同意**「不要追准确率」：本轮把可达率从 5/16 提到 8/16 是靠修一个判定逻辑
（是否给重复折扣），纯工程、零训练成本。先把这类「明显写错」的地方修完，
再谈天花板更公允。

## 十一、第六轮：跨假设 gram 打通（2026-11-11）

按上一轮结论，补齐「可比较的语言模型分数」。

### 做了什么

1. **JNI 入口** `nativeQueryGramScore(schema, context, word)`：
   按 schema 造 `Config`，再 `Grammar::Require("grammar")->Create(config)`
   得到 `Octagram`，调用 `Query(context, word, false)`。按方案缓存实例。
2. **Kotlin API** `RimeEngine.queryGramScore`，`GRAM_UNAVAILABLE` 标记无信号。
3. **接入滑动排序**：`GlideKeyboardController.gramDelta` 以本次首个候选为基准
   转成相对增量，按 `GRAM_WEIGHT=1.0` 并入候选分。无信号时静默退回原排序。

### 真机验证（真实 IME 进程日志）

```
GramSelfCheck: schema=rime_ice 起来=-3.558 起凉=-9.839 可用=true
```

区分度 6.28 个 ln 单位。对比几何分差（本批样本只有 0.5~2），
说明 gram 足以在「几何难分」时定夺，这正是 g111046-12 这类样本需要的信号。

### 排查中发现的部署问题

内置 `XimeGboard.gram`（26MB）此前**没有落到设备 rime 目录**。
原因是我的验证方式踩了坑：instrumentation 进程与 IME 进程的
SharedPreferences 不共享，在测试里调用 `GramBundledModel.ensureDefault`
既看不到写入、也不会留下 `gram_model.xml`。
真实启动 App 后模型正确落盘、偏好正确写入（active_language=XimeGboard）。

**这对以后的真机测试是个重要约束**：涉及偏好/引擎状态的验证必须走真实进程，
不能依赖 instrumentation 里的 targetContext。

### 一个必须留意的回归

接入 gram 后，纯 JVM 单测里 `RimeEngine` 加载不了 native 库
（NoClassDefFoundError），一度打挂 4 个 glide 测试。

不只是为了让测试过——真实场景下方也可能没挂语法模型。

## 十二、第七轮：编辑器前文接入（2026-11-11）

gram 通道打通后，最关键的发现是：**没有前文时它毫无区分度**。

### 实测数据（真机真实进程日志）

| 情况 | 起来 | 起凉 | 区分度 |
|---|---|---|---|
| 空 context | -12.0 | -12.0 | **0.0** |
| 有 context「我们」 | -3.56 | -9.84 | **6.28** |

空 context 时两词都落到 `non_collocation_penalty`，完全一样。
这印证了文档的判断：**独立查询不带前文 → gram 退化成无条件词频**。
所以前文接入不是优化项，是必要项。

### 实现

- `XimeInputMethodService.glidePrecedingText`：复用既有的
  `readTextBeforeCursorWindowed()`，只取末尾 8 字（gram 的
  `collocation_max_length` 默认 5，再多只是白读字符串）
- `GlideKeyboardController.precedingText` + `gestureContext`：
  **只在手势开始（onDown）取一次**，因为读 InputConnection 有开销，
  且同一次手势里前文不会变
- `KeyboardLayout` 把 service 的 provider 注入 controller
- `gramDeltaFor` 改用 `gestureContext` 而非空串

### 边界处理

拿不到前文（宿主不支持 getTextBeforeCursor、或用户都没输入过）时
`gestureContext` 为空串，gram 退回无条件词频——与改动前行为一致，不会更差。

## 十三、第八轮：排序改为 log-domain（2026-11-11）

把 `lookupHypotheses` 的五项混加改成统一量纲相加。

### 改前 vs 改后

| 项 | 旧形式 | 新形式 |
|---|---|---|
| 几何 | `-(h.cost - best)` | `-h.cost` |
| Rime 位次 | `-i * 0.45`（手感值） | `-i * RANK_LOG_STEP`，0.4 ≈ -ln(2/3) |
| 短语连贯 | `coherent*1.1 + depth*1.1*0.7 - short*1.1` | `(coherent + depth*0.7 - short) * ln2` |
| 假设先验 | `-hIdx * 0.15` | `-hIdx * 0.15`（不变） |
| gram | `gramDelta` | 不变（本身就是 ln P） |

### 等价性分析

- 几何项：`-(h.cost - best)` 与 `-h.cost` 只差常数 `best`，**排序完全等价**
- 短语项：新值 = 旧值 × ln2 ≈ 0.693，量级收敛到与其他 log 项匹配
- Rime 位次：0.45 换成 0.4，后者有「位次概率按 2/3 衰减」的含义

### 实测

| 指标 | 改前 | 改后 |
|---|---|---|
| 真实 top-1 | 5/16 | 5/16 |
| 几何可达 | 8/16 | 8/16 |
| 理想轨迹 top-1 | 4/5 | 4/5 |
| GlidePhraseRankingTest（整句簇优先） | 通过 | 通过 |

**没有回归**。但也要诚实说：**也没有提升**——这一轮是打地基，不是提分。
它的价值在于：以后调 gram 权重、加新特征时，各项终于在同一把尺子上。

### 新增守护

`GlideScoreScaleTest` 两项：
- `rimeRankLogProb` 线性于位次（p0=0, p1=0.4, p2=0.8）
- `phraseLogProb` 一条支撑 = ln2 ≈ 0.693，碎词兜底 = -ln2

这两个数值现在有明确含义，不再是「试出来的」；测试会把它们钉住。

## 十四、第九轮：量化 gram 的实际影响力（2026-11-11）

上一轮做完 log-domain 后，回头核验「GRAM_WEIGHT=1.0 到底意味着什么」。

### 真机实测（rime_ice，同一组同音候选只改前文）

| 前文 | 起来 | 起凉 | 差值 |
|---|---|---|---|
| 空 | -12.00 | -12.00 | 0 |
| 我们 | -3.56 | -9.84 | 6.28 |
| 我们（重复验证） | -3.56 | -9.84 | 6.28 |
| 天气 | -2.18 | -9.24 | 7.06 |

### 发现一处文档与实现不符

原注释写的是：

> 取 1.0 表示「1 个 ln 单位 ≈ 1 个几何分」，
> 让语义信号能在几何难分时起作用，但不足以推翻明显的几何差距。

**实际不是这样**：gram 差值 6~7，而本批样本的几何分差只有 0.5~2。
语义信号是**决定性**的，不是「辅助」。已按实测数据重写注释。

### 这个偏置是合理的，但风险要写清楚

合理之处：双拼每音节只有两键，几何本来就分不开同音候选
（`li` 与 `lk` 可能只差几像素），这正是需要语言模型的地方。

风险：前文很短或误判时会把排序带偏。缓解措施是——
**拿不到前文时 `gramDelta` 恒为 0**，退化成改动前的行为，不会更差。

### 待验证项

需要等「同音不同词、且频率相近」的样本攒够后，再判断是否要把
GRAM_WEIGHT 下调。目前 16 条样本的 `prefix` 都是空，
恰好是 gram 最弱的情况，不足以评估权重。

## 十五、第十轮：补上「gram 真的能改变排序」这一环（2026-11-11）

上一轮只证明了 gram 能算出有区分度的分数，但没有证明它真的改变了候选顺序。
两者之间还有一层：分数要经过 `lookupHypotheses` 的加权相加才落到排序上。

### 做法

把 `gramScorer` 抽成可注入的 `(context, word) -> Double`：
生产环境默认走 `RimeEngine`，单测可以替换成假实现。
这样既能测排序逻辑，又不改变生产行为。

### 三项验证（几何代价完全相同的两个候选）

| 场景 | 结果 | 含义 |
|---|---|---|
| 无 gram 信号 | `[甲, 乙]` | 退化为原排序，**不会更差** |
| gram 偏好「乙」 | `[乙, 甲]` | **确认 gram 能翻转顺序** |
| 几何劣势明显（cost 1 vs 8） | `[甲, 乙]` | gram 不会不合理地压倒几何 |

第三项是刻意加的边界守护：它锁住「gram 是加分项而非决定项」，
避免以后调大 `GRAM_WEIGHT` 时把几何信号彻底淹没。
注意这与上一轮实测的「gram 差值 6.28 远大于几何分差 0.5~2」并不矛盾——
真实场景里两个候选的几何差距通常就在 0.5~2 区间，
而几何差距大到 7 以上（cost 1 vs 8）时 gram 仍会退让。

## 十六、第十一轮：真机端到端验证的坑与突破（2026-11-11）

上一轮我放弃了端到端验证，说「卡在 UI 导航」。这一轮定位到**真正原因**，
并打通了所有前置条件。

### 三个真正的原因（都不是代码问题）

1. **输入法被 fcitx5 抢走了**
   `dumpsys input_method` 显示 `mCurMethodId=org.fcitx.fcitx5.android`。
   我一直在用 fcitx5 的键盘做「滑动测试」——当然没有任何反应。
   **这是最耗时也最容易被忽略的坑**：切 IME 后要立刻验证，
   而且 App 重启/切页都可能被系统回退到上一个输入法。

2. **方案不是小鹤双拼**
   设备上一直是 `wubi86_pinyin`，滑动解出的编码在五笔拼音音节表下大量非法。
   `SettingsPreferences.setCurrentSchema` 在 instrumentation 进程里写不进真实偏好
   （进程隔离），直接改 `kime_settings.xml` 也会被 App 启动时的状态写入覆盖。

   **唯一可靠路径**：设置 → 输入方案 → 「方案预设」里点「小鹤双拼」
   → 等待「正在部署方案…」完成。实测这一步会把 `current_schema`
   正确写成 `double_pinyin_flypy`。

3. **`adb input motionevent` 无法模拟滑动**
   逐点 DOWN/MOVE/UP 会被 IME 当成**连续点击**，每一下都打出一个字符
   （实测得到「6~」这样的乱码）。`adb input swipe` 能触发 glide,
   但只能给起终点，无法构造带中间转折的双拼路径。

   **结论：adb 无法做双拼滑动的端到端验证。**
   这不是配置问题，是工具能力的边界。

### 打通的部分

- 小鹤双拼方案已正确部署（键盘空格键显示「小鹤双拼」）
- `adb input swipe` 能触发 glide 并产生候选（实测从 n 滑到 k，
  候选栏出现「那/年/女/难/内/你」）
- 说明**滑动手势 → 解码 → 候选**这条链路在真机上是通的

### 这意味着什么

端到端准确率验证**只能靠人工滑动**。程序侧能做的上限是：

| 层次 | 可自动化 | 已覆盖 |
|---|---|---|
| 几何解码 | ✅ JVM 回放真实轨迹 | GlideTraceReplayTest |
| 候选排序 | ✅ JVM 注入假 gram | GlideGramRankingTest |
| gram 打分 | ✅ 真机调用 native | GlideGramImpactDeviceTest |
| **手势→候选的完整链路** | ❌ 只能人工 | —— |

所以「改完之后准确率有没有变好」这个问题，
**必须由你手动滑几笔才能回答**，我给不出自动结论。

### 重要发现：g-7 的期望本身可能不成立

g-7 期望 `yipwwogu`（其中有连续两个 `w`），实际解出 `yipwyogu`。

```
轨迹: y u i o p o i u y t r e w e r t y u i o i u j h g h y u
```

**真实手指不可能不经过中间的 o/i/u/y/t/r/e**。所以 `p → w` 这种跳法在物理上不成立，
解码器读成 `p → y`（y 在路径上且更早出现）是合理的。

**结论：这条样本的标注可能是笔误或场景不现实，不应作为改进目标。**

## 二十一、第十六轮：样本自检工具，识别出 3 条物理不可能达成的标注（2026-11-11）

### 真正的问题：标注要求了物理上不可能的动作


用户手势是 `w → (跨行) → u → (跨行) → w`，只经过 `w` 两次；

判据：滑动的本质是「手指经过一串键」，所以标注里要求的

实测 16 条样本：

```

  g111046-7:  w×2/1
  g111046-14: k×2/1
  g111046-15: x×2/1
```

**16 条里有 4 条不该作为改进目标**，真实可用样本约 12 条。

前几轮我反复对着这些样本调参，指标不动，还怀疑是自己改错了。
现在有了自检工具，**改之前就知道哪些样本不该追**。
这不提升准确率，但能避免把时间浪费在无解的问题上。

## 二十二、第十七轮：dwell 漏检修复，平均距离 1.56→1.44（2026-11-11）

### 根因

`dwellPositions` 要求「出现一次 >= 120ms 的单次时间空洞」，
但**手指静止时设备仍以 3~4ms 的间隔持续上报同一坐标**，该条件几乎永不成立。

| 判据 | 20 条样本检出停留点 |
|---|---|
| 旧（需单次空洞） | **11 个** |
| 新（仅需总时长） | **174 个** |

按期望编码推算应有 160+ 个按键停留，**旧判据漏检率超过 90%**，
这意味着 `SKIPPED_DWELL_COST` 这个惩罚从上线以来几乎从未生效。

**162 个检出点里有 153 个落在期望编码对应的键上（94%）**。
半径约束负责挡住「慢速连续经过」——途经时手指持续移动，位移会超出半径。

### 实测收益

| 指标 | 改前 | 改后 |
|---|---|---|
| 平均编辑距离 | 1.56 | **1.44** |
| g-15 | wuqiytxx | **wuwwqiytxx**（完全正确） |
| g-16 | 正解第 5 位 | **正解第 1 位**（只差 1 键） |

### 修正上一轮的错误结论

上一轮我用「连续重复键次数 vs 轨迹段数」判定 g-7/g-14/g-15 三条
「物理上不可能达成」。**其中 g-15 是误判**——
真正的原因是我的 dwell 检测漏检，导致轨迹被切碎、段数统计偏少。

## 二十七、第二十二轮：验证 gram 确实生效，排除一处误判的「bug」（2026-11-11）

前几轮打通 gram 后，从没在排序层面确认它真的参与了计算。本轮补上。

### 结论一：gram 在 flypy 方案上确实可用

曾怀疑只有 `rime_ice.custom.yaml` 带 grammar patch，回放用的
`double_pinyin_flypy` 没有 → gram 会返回 UNAVAILABLE。真机验证证伪：

```
flypy:    起来=-3.558 起凉=-9.839 差=6.281
rime_ice: 起来=-3.558 起凉=-9.839 差=6.281
```

两者一致。Octagram 按 language 名 `XimeGboard` 加载全局 .gram 文件，
grammar 配置来自全局 patch，不需要每个方案单独配。

### 结论二：gramBaseline 跨批沿用不是 bug

发现 `gramBaseline` 只在 `onDown` 重置，而预览与最终解码都会调用
`lookupHypotheses`，一度以为基准会跨批泄漏。

实测：在 `lookupHypotheses` 入口加重置 vs 不加重置，
真机端到端回放**两版指标完全相同**（6/16、平均距离 1.44）。

原因：泄漏只给整批候选加**相同的常数偏移**，而排序依据是批内分差，
常数会抵消。**已回退该无意义改动**，并删掉抓不住差异的测试。

### 结论三：gram 真的参与了排序（6.0 的权重不是摆设）

用两个几何同价、gram 差 6.0 的候选验证：分差 = 6.0（gram） + 0.4（位次）
= **6.4**，与预期一致。

这里踩到一个测试陷阱：`gramDeltaFor` 在 `currentSchema.isEmpty()` 时直接返回 0。
只反射调 `lookupHypotheses` 而不走 `onDown`，gram 会被整体绕过，
测出的分差只有 0.4（全是位次惩罚）。**测试必须走完整手势路径**。

### 产出

`GlideGramBaselineScopeTest`（2 项）把上述理解固化，避免后人重走。
全量 1726 项，仅 4 个既有基线失败。

在 `run_code` 的模板字符串里，正则的反斜杠与 PowerShell 引号嵌套会失效，
**写入根本没有发生**。核对源码 `LastWriteTime` 才发现：
四次「扫描」测的都是同一个 0.8f / 128 版本。

改用 `edit` 工具逐处替换、并每次读回确认后，真实数据如下。

### 重测：REPEAT_COST（P1 相关）

| 值 | 完全一致 | 平均距离 |

| 0.0 | 3/16 | 2.06 |

0.8~1.6 是平台区，0.8 已足够。之前记录的「0/5 无变化」是假数据。

### 重测：MAX_SAMPLES（P0，推翻上一轮结论）

| 值 | 完全一致 | 平均距离 |
|---|---|---|
| 64 | 5/16 | 2.00 |
| 80 | 6/16 | 1.81 |
| **96** | **6/16** | **1.38** |
| 112 | 5/16 | 1.69 |
| **128（当前）** | **6/16** | **1.44** |
| 320 | 6/16 | 1.81 |

上一轮写「128 与 320 完全相同」是错的——实际 320 明显更差（1.81）。
P0 的方向没错（采样过多确实有害），只是结论反了。

96 复跑两次均为 1.38，可复现。但**没有采纳**，理由：

1. 曲线极不平滑（80→1.81、96→1.38、112→1.69），是样本噪声而非规律
2. 收益仅 0.06，远小于噪声幅度
3. 128 是长期验证过的稳定值，16 条样本不足以支撑换值

逐条看 96 相比 128：g-4/g-9/g-14 改善共 4 键，g-18 单独变差 2 键，
净收益高度依赖个别样本——典型的过拟合特征。

### 测量流程规范（必须遵守）

1. 改常量一律用 `edit` 工具，**改完立即读回确认**
2. 每次测量前校验 `adb install` 输出含 `Success`，否则报错退出
3. 至少复跑一次确认可复现
4. 参数扫描要看曲线平滑度，孤立最优点一律不采纳

这四条是这轮用错误结论换来的，后续所有调参实验都应遵守。

## 三十、第二十五轮：定位「几何不可达」的真实原因（2026-11-11）

验收标准里「几何候选含正解 ≥60%」只做到 50%，是最大缺口。本轮定位根因。

### 排除法逐层缩小范围

| 检查 | 结果 | 结论 |
|---|---|---|
| TOKENS_PER_SAMPLE 6→12/24/48（单独） | 指标全无变化 | 单独放宽无效 |
| BEAM 10→20/40/100（单独） | 指标全无变化 | 单独放宽无效 |
| limit 16→500 解码 | 可达 **7/16 → 7/16** | 一开始以为正解从未生成 |
| 9 条不可达样本的 reach 覆盖 | **全部有采样点** | 不是 NEAR_DISTANCE 挡的 |
| 9 条的单调对齐 | **全部可对齐** | 不是标注/轨迹不符 |
| **TOKENS=48 + BEAM=100** | **limit500 可达 7→12/16** | ★ 正解被剪枝挤掉 |
| TOKENS=12 + BEAM=20 | limit500 可达 7→10/16 | 温和放宽也有效 |

**关键**：TOKENS 与 BEAM 必须**同时**放宽。单独放宽任一个都无效，
因为 `prune` 里 TOKENS 在 BEAM 之前就截断了候选。
这也解释了此前多轮「放宽剪枝无收益」的结论为什么是错的。

### 逐层 beam dump（g-1，期望 ilwddetmqi）

| 层 | 期望前缀 | 存在 | 正解代价 | 该层最低 |
|---|---|---|---|---|
| L2 | il | ✅ | 1.95 | 1.95 |
| L5 | ilwdd | ✅ | 7.53 | 3.81 |
| L7 | ilwddet | ✅ | **14.56** | **5.78** |
| L8 | ilwddetm | ❌ | — | 6.80 |

正解前缀在 **L8 消失**。该层样例全是 `iiikllll` 这类在少数键上反复对齐的路径，
代价极低；而正解需要跨到 t/m 键，累计代价高出 8.8。

### 但放宽剪枝不能落地

- TOKENS=48 + BEAM=100：端到端测试**跑不完**（beam 爆炸/超时）
- TOKENS=12 + BEAM=20：能跑完，但端到端指标仍是 **6/16、1.44**——
  正解进了候选集，排序阶段仍没把它排到首位

所以真正有两个瓶颈：**剪枝把正解挤掉** + **排序没把正解提上来**。
前者能用参数缓解但会拖慢性能，后者才是最终决定 top-1 的。

### 产出

`GlideReachabilityDiagTest` 用 limit16 与 limit500 对比，
把「正解被截断」与「正解从未生成」区分开，作为长期诊断工具。
所有临时改动已回退，常量保持 TOKENS=6 / BEAM=10。
